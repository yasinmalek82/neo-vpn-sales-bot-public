# تأیید کارت‌به‌کارت با پیامک بلو

قابلیت در این بسته موجود است. پیش‌فرض تنظیمات برنامه خاموش است؛ نصب‌کننده
گزینهٔ فعال‌سازی را می‌پرسد و کلید مستقل می‌سازد.

## رفتار

- فقط قالب پیامک «بلو / واریز پول / … ریال به حساب شما نشست.» پشتیبانی می‌شود.
  مبلغ از جملهٔ واریز استخراج می‌شود؛ موجودی نادیده گرفته می‌شود. ریال باید
  بدون باقی‌مانده به تومان تبدیل شود. تاریخ جلالی با منطقهٔ زمانی تهران خوانده می‌شود.
- هر سفارش دارای ماندهٔ کارت، یک مبلغ ثابت با خرده‌مبلغ `1..999` تومان می‌گیرد.
  قیمت پایه، تخفیف و سهم قبلی کیف پول تغییر نمی‌کنند. مبلغ کامل در فاکتور نمایش
  داده می‌شود و خرده‌مبلغ در همان تراکنش تأیید، یک‌بار به کیف پول برمی‌گردد.
  تأیید دستی هم همین مبلغ و همین برگشت را استفاده می‌کند.
- کل مبلغ برای آن حساب **برای همیشه رزرو** می‌ماند، حتی بعد از انقضا یا رد.
  رزرو به قیمت‌های نزدیک هم برخورد نمی‌کند. اگر همهٔ گزینه‌ها پر باشند، سفارش
  از مسیر عادی رسید دستی ادامه پیدا می‌کند؛ هرگز مبلغ قدیمی به سفارش جدید داده نمی‌شود.
  برای یک قیمت ثابت، حداکثر 999 رزرو ممکن است؛ قیمت‌های نزدیک می‌توانند این ظرفیت را کمتر کنند.
- مهلت تطبیق، حداکثر 30 دقیقه از ساخت سفارش است؛ تنظیم کوتاه‌تر انقضای سفارش
  رعایت می‌شود. رسیدن پیامک بعد از مهلت، تاریخ نامعتبر، مبلغ نامنطبق، تغییر کارت،
  سفارش رد/منقضی یا قبلاً پرداخت‌شده، بررسی دستی می‌خواهد. سفارش منقضی احیا نمی‌شود.
- پیامک بلو شناسهٔ تراکنش و شمارهٔ حساب ندارد. کلید تکرار از حساب تنظیم‌شده، مبلغ
  و دقیقهٔ بانکی ساخته می‌شود؛ تفاوت نام، موجودی یا شکل ارقام آن را عوض نمی‌کند.
  دو واریز واقعاً یکسان در یک دقیقه قابل تفکیک نیستند؛ دومی خودکار مصرف نمی‌شود.
  زمان پیامک تا دقیقه دقت دارد و دقیقهٔ ساخت فاکتور پذیرفته می‌شود.
- متن کامل پیامک، نام صاحب حساب و موجودی ذخیره یا لاگ نمی‌شوند. مبلغ، زمان،
  اثرانگشت رویداد، نتیجه و ارتباط سفارش برای حسابرسی ذخیره می‌شوند.
- تأیید، ثبت پیامک، گزارش‌ها و برگشت خرده‌مبلغ یک تراکنش دارند. فعال‌سازی از
  `provision_recovery` و تحویل از `delivery_outbox` ادامه پیدا می‌کند. در نسخهٔ ۱ هر دو صف هر ۵ ثانیه بررسی می‌شوند و سفارش
  تازهٔ تأییدشده از مسیر بلو انتظار اولیهٔ یک‌دقیقه‌ای ندارد. خطای پنل باعث گم‌شدن پرداخت نمی‌شود.

## تنظیم سرور، فقط در زمان فعال‌سازیِ مجاز

| تنظیم | مقدار |
| --- | --- |
| `BANK_SMS_ENABLED` | پیش‌فرض `false`؛ پس از آماده‌سازی `true` |
| `BANK_SMS_TOKEN` | راز تصادفی مستقل با حداقل 32 کاراکتر؛ هرگز توکن ربات نباشد |
| `BANK_SMS_SENDER` | برچسب مشترک با Shortcut؛ در فایل حاضر `BLUE` |
| `BANK_SMS_ACCOUNT_KEY` | شناسهٔ داخلی ثابت مثل `blu-main`، حداکثر 64 کاراکتر |
| `BANK_SMS_URL` | `https://YOUR-HOST/bank-sms/blu` بدون query یا fragment |
| `SCHEDULER_ENABLED` | باید `true` باشد |

کارت مقصد از همان `get_payment_info` فعلی خوانده می‌شود: تنظیم ذخیره‌شدهٔ ربات،
سپس تنظیم محیطی. هر بار تغییر کارت، فاکتورهای قبلی به بررسی دستی می‌روند.
`BANK_SMS_ACCOUNT_KEY` را برای همان حساب تغییر نده؛ با تعویض کارت همان حساب هم
باید ثابت بماند. پاک‌کردن رزروها یا ساخت کلید جدید برای دورزدن ظرفیت، حفاظت واریز
دیرهنگام را از بین می‌برد. پشتیبان باید این دو جدول جدید را هم نگه دارد.

گیرنده در حالت polling و webhook روی HTTP server فعلی و پورت `WEBHOOK_PORT`
نصب می‌شود و به روشن بودن پنل وب وابسته نیست. TLS معتبر باید در reverse proxy
پایان یابد؛ مسیر را بدون تغییر بدنه به همین برنامه برسان. header احراز هویت،
بدنهٔ درخواست و راز را در لاگ proxy ذخیره نکن. مسیر Telegram همان مسیر قبلی است.
ایمیج نسخهٔ ۱ هنگام راه‌اندازی، migrationهای NEO را تا `ze4f5a6b7c8d` اعمال می‌کند.

این روش استعلام بانک یا اثبات هویت پرداخت‌کننده نیست. اعتماد به آیفون مالک،
فیلتر واقعی فرستنده، راز گیرنده و اختصاص درست حساب مقصد است. چون پیامک شمارهٔ
حساب ندارد، یک اتومیشن را برای پیامک چند حساب با یک فرستنده فعال نکن. پرداخت
شخصی با مبلغ دقیق یک فاکتور هم قابل تمایز نیست؛ حساب اختصاصی فروش مناسب‌تر است.

## فایل Shortcut

فایل آمادهٔ امضاشده با ابزار داخلی macOS:
[NEO-Blu-Payment.shortcut](shortcuts/NEO-Blu-Payment.shortcut).
نسخهٔ XML قابل بررسی و بازتولید هم در همان پوشه با پسوند `.unsigned.shortcut` است.
این فایل **فقط placeholder دارد** و هنوز روی آیفون آزمایش نشده است.

1. فایل امضاشده را با AirDrop یا Files به آیفون ببر و به Shortcuts اضافه کن.
2. در اکشن `Get Contents of URL`، آدرس `REPLACE-HOST` را با آدرس آمادهٔ سرور عوض کن.
3. در Headers مقدار `Authorization` را به `Bearer YOUR_PRIVATE_TOKEN` تغییر بده.
   راز را در URL، چت، مخزن یا تصویر منتشر نکن.
4. در JSON مقدار `sender` در فایل حاضر `BLUE` است؛ `BANK_SMS_SENDER` هم باید همین باشد. مقدار `text`
   باید متغیر **Text** متصل به `Shortcut Input` بماند، نه متن ثابت یا کلیپ‌بورد.
5. در Automation یک اتومیشن **Message** بساز: Sender فقط مخاطب ذخیره‌شدهٔ `BLUE`
   که شماره/شناسهٔ واقعی پیامک بانک را دارد،
   Message Contains برابر «واریز پول»، و اجرای بدون تأیید (`Run Immediately` یا
   خاموش کردن `Ask Before Running`، بسته به نسخهٔ iOS).
   فیلد JSON فقط برچسب است؛ احراز منبع پیامک به فیلتر همین اتومیشن وابسته است.
6. اکشن `Run Shortcut` را به `NEO Blu Payment` وصل کن؛ بدنهٔ کامل پیام دریافت‌شده
   را به‌عنوان ورودی بده. در بعضی نسخه‌ها باید ویژگی Text/Content پیام را انتخاب کنی.
   اگر عنوان فرستنده یا توصیف شیء به‌جای بدنه ارسال شود، سرور آن را رد می‌کند.
7. مجوز دسترسی به دامنه را در اولین اجرای کنترل‌شده بده؛ اجرای هنگام قفل بودن را
   روی همان آیفون آزمایش کن. تغییر نسخهٔ iOS ممکن است نام گزینه‌ها را عوض کند.

اگر فایل درست وارد نشد، معادل دستی فقط دو اکشن است: Text با متغیر Shortcut Input،
سپس Get Contents of URL با POST، بدنهٔ JSON شامل `sender` و `text` و header بالا.
JSON را با اتصال رشته‌ها نساز؛ فیلد متنی Shortcuts خودش newlineها را encode می‌کند.

| پاسخ | معنی |
| --- | --- |
| `200 / approved` | پرداخت ثبت شد؛ کارگرها فعال‌سازی و تحویل را ادامه می‌دهند |
| `200 / duplicate` | پیامک قبلاً ثبت شده؛ پرداخت دوباره ساخته نشده |
| `200 / manual_review` | گزارش بررسی دستی ثبت شد؛ پرداخت خودکار تأیید نشده |
| `400` | قالب/فرستنده/بدنه پشتیبانی نمی‌شود؛ تنظیم را اصلاح کن |
| `401` | راز گیرنده نادرست است |
| `409` یا `503` | ثبت تراکنش کامل نشده؛ همان پیامک را دوباره ارسال کن |

این Shortcut صف آفلاین یا ارسال مجدد تضمین‌شده ندارد. قطع اینترنت آیفون یا
دسترسی نداشتن به سرور، تأیید را عقب می‌اندازد؛ رسید دستی مشتری مسیر جایگزین است.

## گیت فعال‌سازی

قبل از استفادهٔ واقعی: نسخهٔ تأییدشده، پشتیبان، schema، HTTPS و کارگرها آماده باشند.
در محیط آزمایشی مستقل، یک پرداخت مجازِ کوچک برای فاکتور زنده را از پیامک واقعی
تا ثبت وجه و دریافت یک کارت سرویس دنبال کن؛ همان پیامک را دوباره بفرست و تأیید کن
اعتبار/سرویس دوم ایجاد نمی‌شود. قطع اینترنت و واریز دیرهنگام را هم بررسی کن.
خاموش‌کردن `BANK_SMS_ENABLED` گیرنده و رزرو جدید را متوقف می‌کند؛ فاکتورهای قبلی
همچنان مبلغ ثابت و امکان بررسی دستی دارند. هیچ آزمایش بانکی/آیفون واقعی در تست‌های محلی انجام نشده.
